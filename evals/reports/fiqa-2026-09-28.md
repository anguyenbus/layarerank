# How LayaReranker performs on FiQA

*2026-09-28 · BEIR FiQA-2018 test · BM25 top-30 · 385 queries · laya 0.3.21 · torch 2.14.0+cu126 · RTX 3090 Ti*

## Summary

- **Fully fine-tuned, Laya matches bge-reranker-v2-m3.** Training all 421M parameters on FiQA's train
  split for 1.74 epochs (selected on dev; 60 minutes on one GPU) gives **0.580 nDCG@10**. bge gets
  **0.578**, a difference of **+0.002 [−0.016, +0.020]**. Laya's MRR@10 (0.737 vs 0.741) and Recall@10
  (0.632 vs 0.633) also match bge's, and it is still ~22% faster per passage (9.8 vs 12.6 ms).
- **Blending the two beats either one.** The fine-tuned model and bge make different mistakes (Laya wins
  104 queries, bge 116, 165 ties). A 50/50 blend of their normalised scores reaches **0.600 nDCG@10,
  +0.022 [+0.010, +0.035] over bge** (§6), at the cost of running both models.
- **Off-the-shelf Laya does not pass the gate.** The best configuration, English checkpoint with the
  `noul-dict-bare` prompt, reaches 0.422 nDCG@10 against 0.392 for BM25: +0.031 [−0.004, +0.064],
  which is **NO-GO**. bge is 0.156 ahead of it.
- **Fine-tuning the encoder is what matters.** Training only the decision head (6% of parameters)
  reached 0.448 (+0.057 over BM25, GO), but plateaued. Adding the encoder reached **+0.188 [+0.159,
  +0.220] over BM25** and +0.131 over the head-only model.
- **What fine-tuning fixed.** Separation of relevant from non-relevant passages rose to bge's level
  (AUC 0.834 → **0.933**; bge 0.929). The damage untrained Laya did on queries BM25 already ranks well
  became a gain (0.559 → 0.757; BM25 0.734).
- **Caveat: fine-tuning makes Laya a FiQA specialist; bge is general-purpose.** The tie holds on FiQA
  test data; it is not known how the fine-tuned model does on other domains (§8).
- **Recommendation:** for FiQA-like data, the fully fine-tuned checkpoint is a drop-in match for bge at
  lower latency. Blend it with bge where the extra ~2 points justify the cost. Make `noul-dict-bare` the
  default prompt. Test on a second dataset before generalising.

### What the configuration sweep shows

1. **Prompt wording matters most.** The three yes/no (`noul`) prompts all beat the 4-level `score`
   question, and the version with the least instruction text is best. The long true/false criteria in the
   default preset slightly hurt. Laya's docs report the same effect on the English checkpoint: "`noul` can
   follow its option labels instead of the state" (upstream issue #156).
2. **Truncation is not what limits quality.** About 10% of passages are cut at the 512-token limit.
   `window_max` scores long passages in overlapping windows and keeps the highest score, which brings
   truncation to about 0%. nDCG does not improve, and scoring costs 15–20% more.
3. **Use the English checkpoint.** typed-decisions and multilingual both allow 1024 tokens and see nearly
   every passage in full, but they rank worse. typed-decisions only matches BM25 and is 50% slower;
   multilingual is *significantly worse* than BM25.

## 4. How Laya behaves

### 4.1 Separating relevant from non-relevant passages

The table shows the average, over queries, of how often a relevant candidate outscores a non-relevant
one (per-query AUC over the 30 candidates):

| System | AUC |
|---|---|
| laya multilingual noul-dict | 0.750 |
| bm25 | 0.770 |
| laya english score-dict | 0.808 |
| laya typed-decisions noul-dict | 0.814 |
| laya english noul-dict | 0.825 |
| laya untrained (`noul-dict-bare`) | 0.834 |
| laya head-FT | 0.848 |
| bge-reranker-v2-m3 | 0.929 |
| **laya full-FT** | **0.933** |

Untrained Laya already beats BM25 at telling relevant from non-relevant, but most of that advantage is
spent low in the list. Recall@10 rises by +0.051 over BM25 while MRR@10 rises by only +0.021: Laya gets
relevant passages into the top 10 without reliably putting the best one first. Head-only fine-tuning
barely changed that (AUC +0.014). **Full fine-tuning closed the gap to bge completely**: AUC 0.933 and
MRR@10 0.737, against bge's 0.929 and 0.741.

### 4.2 Hard and easy queries

Queries grouped by how well BM25 ranks them (nDCG@10). The grouping is by BM25's own score, so some
regression to the mean is built in. bge is shown as a control for that effect.

| Query group | n | bm25 | Laya untrained | Laya head-FT | **Laya full-FT** | bge |
|---|---|---|---|---|---|---|
| BM25 misses (nDCG = 0) | 75 | 0.000 | 0.339 | 0.351 | **0.470** | 0.410 |
| BM25 middling (0 < nDCG < 0.5) | 169 | 0.279 | 0.345 | 0.358 | **0.480** | 0.479 |
| BM25 already good (nDCG ≥ 0.5) | 141 | 0.734 | 0.559 | 0.608 | **0.757** | 0.785 |

- **Untrained Laya helps hard queries and hurts easy ones.** It recovers about 0.34 nDCG where BM25
  fails, but loses 0.175 on queries BM25 already handles. bge *gains* 0.05 there, so regression to the
  mean cannot explain the loss.
- **Head-only fine-tuning reduced that loss** to 0.126.
- **Full fine-tuning removes it:** 0.757 on those queries, above BM25's 0.734. On queries BM25 misses
  entirely, full-FT Laya (0.470) is **ahead of bge (0.410)**; bge stays ahead on the easy group. This
  difference in strengths is why blending the two helps (§6).

### 4.3 Score distribution and thresholds

Laya's `noul` score is a probability in [0, 1]. The layarank reference library filters out candidates
below 0.2 by default.

| Model / preset | Median score, relevant | Median score, non-relevant | ≥ 0.2: relevant kept | ≥ 0.2: non-relevant kept | ≥ 0.5: relevant kept | ≥ 0.5: non-relevant kept |
|---|---|---|---|---|---|---|
| **full-FT noul-dict-bare** | **0.749** | **0.043** | 91% | **21%** | **72%** | **7%** |
| head-FT noul-dict-bare | 0.457 | 0.170 | 91% | 42% | 40% | 6% |
| untrained noul-dict-bare | 0.672 | 0.150 | 88% | 40% | 68% | 21% |
| untrained noul-dict | 0.637 | 0.247 | 95% | 59% | 69% | 23% |
| untrained noul-text | 0.673 | 0.221 | 93% | 54% | 70% | 23% |
| untrained score-dict (normalised) | 0.725 | 0.594 | 100% | 95% | 97% | 74% |
| untrained typed-decisions noul-dict | 0.601 | 0.440 | 100% | 92% | 80% | 37% |

Untrained Laya is a loose filter. At the 0.2 default it still passes 40% of non-relevant candidates.
**The full-FT model is the first version usable as a filter:** most non-relevant passages score near 0
(median 0.043). At 0.5 it keeps 72% of relevant passages and only 7% of non-relevant ones; at 0.2, 91%
and 21%. Neither fine-tuned checkpoint had its temperatures re-fitted, so the probabilities are not
calibrated; pick any threshold on held-out data.

### 4.4 Long passages

Only 49 of the 385 queries have no truncated candidate. On those 49, untrained Laya gains +0.101 over
BM25, compared with +0.020 on the 336 queries that include truncated candidates. bge shows the same drop
(+0.266 vs +0.175), so most of the gap reflects how hard those queries are, not truncation. The
window_max result (§3) confirms this: showing Laya the full passage does not help. The full-FT model sees
the same 9.1% truncation as untrained Laya and still ties bge.

### 4.5 Speed and reproducibility

- **Speed:** on the RTX 3090 Ti, Laya takes 9.8 ms per pair (about 0.30 s per 30-candidate query), the
  same before and after fine-tuning. bge takes 12.6 ms per pair without any tuning (fp32, batch 16). At
  equal quality, **full-FT Laya is about 22% faster than bge**. On CPU, Laya was about 6.7 s per pair in
  an earlier partial run.
- **Rounding:** Laya returns `noul` probabilities rounded to 4 decimals. There are 29.3–29.8 distinct
  scores per 30 candidates, and ranks 10 and 11 are tied in at most 1.6% of queries (full-FT).
- **Reproducibility:** the default preset scored on CPU and on GPU agrees within 0.001 nDCG@10 on the same
  50 queries. bge's CPU and GPU runs agree exactly on those 50 queries.

| Blend | CV α | nDCG@10 | vs BM25 | vs the same Laya alone |
|---|---|---|---|---|
| untrained + BM25 | 0.5 / 0.6 | 0.4725 | +0.081 [+0.060, +0.103] | +0.051 [+0.030, +0.073] (α = 0.5) |

- **Limits:** one dataset and one simple blending scheme. Rank-based fusion (RRF) or a z-score blend may
  do better.

## 6. Laya combined with bge

These are simulated from the stored per-query scores. Both models score every passage independently, so
a cascade's ranking is exactly what a live cascade would produce. Latency per query is the sum of each
stage's measured per-pair cost.

- **bge → Laya top-N:** bge ranks all 30, then Laya reorders bge's top N. The rest keep bge's order.
- **Laya → bge top-N:** the same, with the roles swapped.
- **Score blend:** `α · laya + (1 − α) · bge` on min-max normalised scores, with α chosen by 2-fold
  cross-validation.

nDCG@10 with each Laya model (bge alone = **0.578**):

| Approach | Untrained | Head-FT | **Full-FT** | ms / query | Full-FT: Δ vs bge alone [95% CI] | Full-FT: wins / ties / losses vs bge |
|---|---|---|---|---|---|---|
| Laya alone | 0.422 | 0.448 | 0.580 | 295 | +0.002 [−0.016, +0.020] | 104 / 165 / 116 |
| bge → Laya top 3 | 0.554 | 0.563 | 0.588 | 409 | +0.010 [−0.002, +0.022] | 57 / 285 / 43 |
| bge → Laya top 5 | 0.529 | 0.543 | **0.593** | 428 | **+0.015 [+0.001, +0.030]** | 84 / 229 / 72 |
| bge → Laya top 10 | 0.493 | 0.509 | 0.586 | 478 | +0.008 [−0.008, +0.024] | 102 / 181 / 102 |
| bge → Laya top 20 | 0.439 | 0.462 | 0.583 | 576 | +0.005 [−0.013, +0.023] | 104 / 168 / 113 |
| Laya → bge top 3 | 0.466 | 0.488 | 0.588 | 333 | +0.010 [−0.004, +0.024] | 100 / 210 / 75 |
| Laya → bge top 5 | 0.492 | 0.513 | 0.584 | 358 | +0.006 [−0.006, +0.017] | 99 / 235 / 51 |
| Laya → bge top 10 | 0.527 | 0.532 | 0.582 | 421 | +0.004 [−0.005, +0.013] | 80 / 283 / 22 |
| Laya → bge top 15 | 0.563 | 0.564 | 0.585 | 485 | +0.007 [+0.004, +0.011] | 50 / 332 / 3 |
| Laya → bge top 20 | 0.572 | 0.579 | 0.580 | 549 | +0.003 [+0.001, +0.005] | 26 / 358 / 1 |
| **Score blend** (CV α: untrained 0.1; head-FT 0.2–0.3; **full-FT 0.5–0.6**) | 0.580 | 0.576 | **0.600** | 674 | **+0.022 [+0.010, +0.035]** | 112 / 201 / 72 |

- **Untrained or head-FT, Laya only makes bge worse.** Every cascade loses to bge alone, and the best
  score blend is 80–90% bge and merely ties it.
- **Full-FT Laya and bge are complementary.** They are equally good but win on different queries (§4.2),
  so combining them helps. The score blend is best: **+0.022 nDCG@10 and MRR@10 0.774**, significant,
  and in the cross-validation it put roughly equal weight on both models.
- **Cascades help less.** Letting full-FT Laya reorder bge's top 5 gains +0.015 (just significant).
  Laya → bge cascades gain at most 0.010 and mostly within noise.
- **Cost:** the blend runs both models on every candidate: 674 ms per query against 295 for Laya alone
  and 379 for bge alone. A 2-point gain has to be worth roughly doubling the reranking compute.

## 7. Fine-tuning

### 7.1 Setup

Both runs use `evals/finetune.py` with the same data, labels, loss and selection rule. The only
differences are which parameters train and the schedule.

| | Head-only (`ft-fiqa-head`) | Full model (`ft-fiqa-full`) |
|---|---|---|
| Command | `python -m evals.finetune --dataset fiqa --out ft-fiqa-head --head-only` | `python -m evals.finetune --dataset fiqa --out ft-fiqa-full --epochs 3 --evals-per-epoch 4 --patience 4` |
| Trained parameters | Decision head (2 transformer layers, 25.2M) + scorer (1.1M) + question-type embedding: **~26M of 421M**. Encoder frozen, in eval mode. | **All 421M** (encoder 395M + head). Gradient checkpointing on the encoder and head. |
| Learning rate | head 1e-4 | encoder 1e-5, head 1e-4 |
| Epoch cap / dev checks / patience | 5 / every ½ epoch / 2 | 3 / every ¼ epoch / 4 (one epoch without gain) |
| Speed | 0.72 s per step | 2.4 s per step |
| Selected checkpoint | epoch 4.5 (step 1737) | epoch 1.74 (step 672) |
| Wall time | ~38 min | ~60 min (stopped early at epoch 2.74) |

Shared by both runs:

| | |
|---|---|
| Base | `convaiinnovations/laya` (English checkpoint), prompt `noul-dict-bare` (unchanged at inference) |
| Labels | FiQA **train** qrels on each train query's BM25 top-30. Positive (1) = candidate judged relevant, 1.53 per query on average. Negative (0) = any other top-30 candidate, i.e. BM25's hard negatives. |
| Examples per step | 8 queries; per query, all positives in the pool plus 7 negatives resampled every epoch (~70 rows per step) |
| Encoding | Exactly as at inference: laya's `_encode_state` on the preset's question, 512-token rows, same truncation |
| Loss | Listwise softmax over each query's candidates on the margin s = z_true − z_false, i.e. −log(Σ_pos e^s / Σ_all e^s), **plus 0.5 × binary cross-entropy** of sigmoid(s) against the label |
| Optimiser | AdamW, weight decay 0.01, 5% warm-up then cosine decay, gradient clipping at 1.0, bf16 autocast, one RTX 3090 Ti |
| Selection | Dev nDCG@10 on the 281 dev queries; keep the best checkpoint; the test split is scored once, afterwards |
| Output | `evals/models/<name>/` (808 MB each, laya checkpoint layout, loadable with `laya.Agent(path)` or the spec `laya:<name>:noul-dict-bare`). Not in git. |

A note on the upstream notebook (`laya_finetune_typed_decisions_2xT4_kaggle.ipynb`): it trains each row
on its own, with soft-label cross-entropy plus a noisy policy-gradient term. Its training script also
saves a config with `max_len=1024` although its data was encoded at 512 tokens. This recipe uses a
listwise ranking loss and keeps 512 tokens throughout, so training and inference see the same inputs.

  encoder was the limit.
- **The full model closed 63% of the gap in a quarter of an epoch** (96 steps) and reached bge's dev
  score after one epoch. From epoch 2 it drifted down slightly while the training loss kept falling
  (about 0.9 → 0.08), which is early overfitting; the patience of one epoch caught it, and the epoch-1.74
  checkpoint was kept.

### 7.3 Test results (385 queries, each checkpoint scored once)

| | Head-FT minus … | Full-FT minus … |
|---|---|---|
| bm25 | +0.057 [+0.022, +0.091] (passes the gate) | **+0.188 [+0.159, +0.220]** (passes the gate) |
| Laya untrained, same prompt | +0.026 [+0.010, +0.043] | +0.158 [+0.136, +0.181] |
| Laya untrained, default prompt (`noul-dict`) | +0.041 [+0.021, +0.059] | +0.172 [+0.148, +0.197] |
| Laya head-FT | — | +0.131 [+0.109, +0.154] |
| bge-reranker-v2-m3 | −0.130 [−0.157, −0.105] | **+0.002 [−0.016, +0.020] (tie)** |

The dev gains carried over to test at a similar size: head-FT +0.035 on dev and +0.026 on test; full-FT
+0.191 and +0.158. On both splits full-FT lands level with bge. There is no sign of overfitting to the
dev queries.

## 8. Caveats

- **Specialist vs generalist.** The fine-tuned checkpoints saw 3,085 FiQA training queries; bge saw none.
  The tie with bge is on FiQA test data only. How full-FT Laya does on other domains, and whether it lost
  general ability, has not been measured. This matters most before using the checkpoint outside finance.
- **One dataset.** FiQA is opinionated financial Q&A with short answers. All conclusions here, including
  which prompt is best and the blend weights, may not transfer.
- **Selection optimism (untrained configurations).** The best untrained preset was picked out of 8 on the
  same test queries it is reported on; its lead over the other `noul` prompts is within noise. The
  fine-tuned checkpoints do not have this problem: they were chosen on dev only.
- **Noisy labels.** FiQA judges about 2.6–2.9 passages per query, and training treats every unjudged
  passage as non-relevant. Some "negatives" are relevant, which caps what training can learn and how well
  the metrics can measure it.
- **The BM25-bucket analysis (§4.2) is descriptive.** Grouping queries by BM25's own score favours BM25 in
  the top group, which is why bge is shown alongside as a control.
- **50-query subsets are misleading.** On the original 50-query sample, `noul-text` passed the BM25 gate
  (+0.103 [+0.004, +0.204]); on all 385 queries it does not. Use the full set for any gate decision.
- **bge was not tuned or fine-tuned.** fp16 and larger batches would make it faster. Fine-tuning bge on
  FiQA would likely raise it too, so the fair comparison of fine-tuned models is still open.

## 9. Recommendations

1. **For FiQA-like data, use the fully fine-tuned checkpoint** (`ft-fiqa-full`). It matches bge on every
   metric and is ~22% faster per passage.
2. **If quality matters more than cost, blend full-FT Laya with bge** (α ≈ 0.5 on min-max normalised
   scores): +0.022 nDCG@10 over bge, at roughly twice the reranking compute. This needs a small API
   change so callers can pass the second model's scores.
3. **Before using the fine-tuned checkpoint elsewhere, test it on at least one other BEIR dataset** (e.g.
   SciFact or NFCorpus) against both untrained Laya and bge, to measure how much general ability it kept.
4. **Change the default preset to `noul-dict-bare`.** It is better or equal on every metric, at no extra
   cost.
5. **Re-fit the yes/no temperature** on dev if scores will be used as a threshold (§4.3). Ranking is
   unaffected by temperature.
6. **Don't use** `window_max`, the 1024-token checkpoints, or head-only fine-tuning for this task. They add
   cost or fall well short of the full fine-tune.
7. **Possible next steps:** fine-tune bge on the same data for a like-for-like comparison, and try a
   mixed-domain training set (e.g. FiQA + MS MARCO) to keep the gain without the specialisation.

## Reproduce

```bash
uv sync --extra gpu --extra eval
# off-the-shelf systems (385 test queries)
for s in bm25 bge laya:english:noul-dict laya:english:noul-dict-bare laya:english:noul-text \
         laya:english:score-dict laya:english:noul-dict:window_max laya:english:noul-text:window_max \
         laya:multilingual:noul-dict laya:typed-decisions:noul-dict; do
  uv run --extra gpu --extra eval python -m evals.run --dataset fiqa --k 30 --system "$s"
done
# fine-tunes (build train/validation pools on first run), then score each result on test
uv run --extra gpu --extra eval python -m evals.finetune --dataset fiqa --out ft-fiqa-head --head-only
uv run --extra gpu --extra eval python -m evals.finetune --dataset fiqa --out ft-fiqa-full \
  --epochs 3 --evals-per-epoch 4 --patience 4
for m in ft-fiqa-head ft-fiqa-full; do
  uv run --extra gpu --extra eval python -m evals.run --dataset fiqa --k 30 --system "laya:$m:noul-dict-bare"
done
uv run --extra gpu --extra eval python -m evals.report --dataset fiqa --k 30 --candidate laya:ft-fiqa-full:noul-dict-bare
```

- Per-query scores are in `evals/results/fiqa.top30/`. The earlier 50-query run, with bge on CPU, is in
  `evals/results/archive-run1-fiqa.top30-50q/`.
- Dev curves and run settings are in `evals/models/<name>/finetune.json` (the model directories are not
  in git).
- The AUC, threshold, query-group, blend and cascade analyses (§4–6) were computed with one-off scripts
  over those files. They are not yet part of `evals/report.py`.
- The head-only run used an earlier, functionally identical version of `evals/finetune.py` (refactored
  for lint afterwards and re-checked with a short smoke run).
